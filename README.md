# Gather · Single-restaurant POS

Phases 1 and 2 of the supplied implementation plan: a working MERN monorepo with staff authentication, role permissions, menu/catalog management, and synchronized floor plans. Later POS modules are explicitly marked as planned. No sales, payments, or inventory endpoints are simulated.

**Upgrading Phase 1:** run `npm run migrate:phase2` with MongoDB running, then sign out and back in. See [Phase 2 guide](docs/phase-2.md) for permissions, workflows and integrity rules. Optional realistic menu data is available through `npm run seed:demo`; the migration itself does not insert business data.

## Requirements

- Node.js 20.19+ (Node 22 recommended for the supplied containers), npm, and Docker Desktop with its engine running.
- Alternatively, provide your own MongoDB replica-set connection in `.env`.
- Internet access for the first dependency install and Docker image download.

## Local setup — Windows PowerShell

Run these commands inside `restaurant-pos`:

```powershell
npm install
npm run setup
docker compose up -d mongo
# Review .env, including the generated owner password, before seeding.
npm run seed
npm run migrate:phase2
npm run dev
```

Open **http://localhost:5173**. Sign in using `SEED_OWNER_EMAIL` and `SEED_OWNER_PASSWORD` from your local `.env`. Setup generates a random password and signing secret; there are no shared default credentials. Setup never overwrites an existing environment file. Seeding is idempotent and never resets an existing owner's password or role.

The API listens on port 4000 and Vite on 5173. Keep the dev command running. `Ctrl+C` stops both processes. After initial setup, `Start POS.cmd` runs the same development command. MongoDB must already be running.

The Mongo container advertises `mongo:27017` within the Docker network. Local tools use `directConnection=true` to connect through its loopback-only published port. Do not remove that flag from the provided local URI.

## Environment

| Variable                  | Purpose                                                             |
| ------------------------- | ------------------------------------------------------------------- |
| NODE_ENV                  | development, test, or production; production enables Secure cookies |
| PORT                      | API port, default 4000                                              |
| API_RATE_LIMIT_PER_MINUTE | Per-IP API allowance, default 600; login retains its separate limit |
| MONGODB_URI               | Database connection; use replica set rs0                            |
| JWT_SECRET                | At least 48 characters; randomly generated by setup                 |
| CLIENT_ORIGIN             | Exact allowed browser origin, including port                        |
| SEED_OWNER_NAME           | Initial administrator display name                                  |
| SEED_OWNER_EMAIL          | Initial administrator email                                         |
| SEED_OWNER_PASSWORD       | Initial password, 14–128 characters; generated by setup             |
| LOG_LEVEL                 | Pino logging level                                                  |

Never commit `.env`. Setup restricts file mode where supported; on Windows, secure the file with your user account's filesystem permissions. Passwords and signing secrets are not printed by setup or seed.

## Available functionality

- Category and menu item creation, editing and safe archiving; search, filters, pagination and availability controls.
- Modifier groups with selection limits, stable choices and integer-minor-unit prices.
- Floors and positioned tables with capacities, shapes, manual status transitions and live updates.
- Optimistic version checks and transactional audit/reference integrity for configuration changes.
- Generated [OpenAPI contract](docs/openapi.json), recreated with `npm run docs:api`.

- Password login using Argon2id hashes (19 MiB memory, two iterations, one lane).
- Five-minute, issuer/audience-validated access JWTs held in client memory.
- Seven-day maximum session life with opaque refresh tokens held in HttpOnly, SameSite=Strict cookies. Only token hashes are stored in MongoDB.
- Atomic refresh rotation; detected reuse revokes the entire affected session. Web Locks serialize rotations across supported same-origin browser tabs.
- Logout revocation, database-checked session status, active-account checks, and immediate backend enforcement of permission changes.
- Owner, Manager, Cashier, Waiter, Kitchen Staff, and Inventory Staff role records. The shared permission map defines their rights.
- Backend-protected, paginated staff directory for Owner and Manager.
- Login and global API rate limits, input validation, origin checks, secure headers, redacted request logging, and authentication audit events.
- Authenticated Socket.IO connection with periodic session validation and permission-checked menu/table change notifications.
- Responsive desktop/tablet layout, collapsible navigation, light/dark mode, skeletons, errors, empty states, confirmation dialog, and accessible labels.
- Five-minute idle lock and **Alt+L** shortcut. Browser session locking signs out of the server; re-entry requires the password.
- Readiness endpoint, graceful shutdown, and versioned API documentation in `docs/openapi.yaml`.

No token is persisted in localStorage. Only theme preference is saved there; sessionStorage contains a non-secret lock flag.

## Project structure

```text
restaurant-pos/
  client/
    src/components/ui/       # shadcn-style primitives with Radix

    src/lib/                 # centralized errors
    src/app.ts               # HTTP middleware and routes
    src/realtime.ts          # authenticated Socket.IO foundation
    src/seed.ts               # roles and initial owner
  shared/src/                # domain types, role permissions, Zod schemas

  scripts/setup.mjs          # local secret generation
```

Business logic lives in the auth service; controllers handle transport and cookies. Mongoose models are the repository boundary. New feature modules should keep that separation and add independent validation and tests.

## Checks

```powershell
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

API tests start an isolated MongoDB 7.0 replica set using mongodb-memory-server. Its first run downloads the official MongoDB binary; normal dependency installation skips that optional download. Browser tests start their own temporary database/API and Vite server on ports 4100 and 5174, leaving the development app on 4000/5173 untouched. Tests never clear or seed the restaurant database. Test-only account credentials are confined to test fixtures.

Coverage includes password hashing, credential errors, permission enforcement, account deactivation, pagination, refresh rotation/replay/concurrency, logout, expiry, origin protection, cookie flags, login rate limiting, socket authentication, browser reload, tablet access restrictions, session locking, and sign-out. Transactional billing and kitchen-event delivery tests will be added with those modules.

## Entire stack in Docker — local evaluation

```powershell
npm run setup
docker compose --profile app up -d --build
docker compose exec server npm run seed -w server
```

Open **http://localhost:8080**. The Compose configuration deliberately runs HTTP development mode bound to the host's loopback interface. It is not a public deployment configuration. The MongoDB data volume persists across restarts. Do not use `docker compose down -v` unless you intend to delete the database.

For production deployment, terminate HTTPS at Nginx or a trusted upstream proxy, set `NODE_ENV=production` and the exact HTTPS `CLIENT_ORIGIN`, configure database authentication and replica-set internal authentication, restrict network access, and configure persistent rate-limit storage if running multiple API processes. The production API port must be accessible only through the single trusted proxy because it trusts one proxy hop. Secure refresh cookies require HTTPS. Use a real secret manager; do not ship seed credentials. Production deployment and hardware integration require later-phase validation.

## Backup and restore

Back up the replica set with `mongodump --archive=/backup/restaurant.archive --gzip --oplog`, using a mounted backup volume and credentials appropriate to your deployment. Encrypt and copy backups off the restaurant host. To restore, stop application writes and restore into a separate isolated replica set with `mongorestore --archive=/backup/restaurant.archive --gzip --oplogReplay`. Check user/role counts and authentication before switching the application connection. Revoke sessions following a disaster recovery. Perform scheduled restore drills; a command example alone is not a verified recovery procedure.

## Phase boundary

Phases 1–2 include authentication, roles, menu configuration, and manual floor/table management, not staff account administration. The main seed creates six roles and one owner account. Optional demo seeding adds menu/floor data, never sales. Trusted-terminal PIN login remains optional and unimplemented. PIN hash storage exists, but no PIN login endpoint is advertised.

Next: Phase 3 — POS cart, server-side order calculations, order lifecycle and table/order assignment. Later phases implement kitchen fulfillment, transactional payment/refund ledgers, printer queues, inventory, shifts, business-timezone reporting, and operational hardening. Do not use this foundation release to take live restaurant payments.
